At HashCash Consultants I architected a multi-tenant Retrieval-Augmented Generation (RAG) chatbot platform. Each tenant gets an isolated knowledge base, and the platform cut manual information-retrieval time by roughly 30%. This post covers the decisions that matter most when one RAG system has to serve many organisations safely.

## Isolation is a requirement, not a feature

In a single-tenant prototype, retrieval is simple: embed the question, find the nearest chunks, answer. With many tenants, the first question changes to: *whose* chunks are you allowed to search?

There are two common approaches:

- **Shared tables, tenant-filtered queries.** Every chunk row carries a tenant identifier and every similarity search filters on it. It's operationally simple, but the filter must be impossible to forget - enforce it in one data-access layer, never in callers.
- **Separate schemas or tables per tenant.** Stronger separation and easy per-tenant deletion, at the cost of more objects to manage and migrate.

## Chunking decides answer quality

Most bad RAG answers are retrieval failures, and most retrieval failures start at chunking. Chunks that are too large dilute the embedding; chunks that are too small lose the context needed to answer.

## Embeddings and pgvector

Embeddings live in PostgreSQL with pgvector. Keeping vectors next to the rest of the data means one database to operate, transactional updates when a document changes, and ordinary SQL for metadata filters such as the tenant.

```sql title="Illustrative: a tenant-scoped similarity search"
SELECT id, content
FROM chunks
WHERE tenant_id = $1
ORDER BY embedding <=> $2
LIMIT 5;
```

## Takeaways

- Enforce tenant isolation in exactly one place and test it like a security boundary.
- Spend more time on chunking and retrieval than on prompts.
- Keep vectors in Postgres until you have a reason not to.
